# 고정익 기체에 TensorFlow Lite for Microcontrollers 적용하기

## 1. 목표와 전제

TFLM(TensorFlow Lite for Microcontrollers)은 PC에서 학습·변환한 작은 모델을 마이크로컨트롤러에서 **추론**하는 런타임이다. 기체의 기존 비행제어기(FC)는 자세 안정화, 항법, 조종권, 페일세이프를 계속 담당한다. 첫 적용 목표는 TFLM이 센서 데이터로 상태를 판별하여 **기록·경고**하는 것이다. [TFLM 개요](https://github.com/tensorflow/tflite-micro/blob/main/README.md), [모델 변환과 MCU 제약](https://github.com/tensorflow/tensorflow/blob/master/tensorflow/lite/g3doc/microcontrollers/build_convert.md)

현재 저장소에는 기체 제원, FC 종류, 센서 목록, 목표 기능이 없다. 아래는 기존 고정익 기체에 적용할 기준 구조이며, 수치와 인터페이스는 실기체 조사 후 확정한다.

### 첫 기능 선택

| 후보 | 입력 예 | 출력 | 적용 순서 |
| --- | --- | --- | --- |
| 비행 상태/이상 징후 모니터링 | 대기속도, 자세, 각속도, 전류, 스로틀, 전압 | 상태 또는 이상 점수 | 첫 시범 기능. 출력은 로그와 경고에 한정 |
| 실속 위험 추정 | 대기속도, 받음각(있을 때), 하중계수, 자세, 조종 입력 | 위험 점수 | 신뢰할 수 있는 계측과 비행 영역별 검증이 필요 |
| 에너지·항속 예측 | 전압, 전류, 대기속도, 고도 변화, 바람 추정 | 잔여 에너지/항속 추정 | 기존 FC의 추정치와 비교 후 사용 |
| 경로·제어 명령 제안 | 상태 추정, 임무, 기체 제약 | 제한된 상위 목표값 | 마지막 단계. 별도의 감시·복귀 설계 필요 |

**권장 시작점:** 비행 상태/이상 징후 모니터링 하나를 읽기 전용으로 구현한다. 입력·출력·판정 기준을 먼저 확정하고, 단순 임계값 또는 규칙 기반 기준선과 비교한다.

## 2. 시스템 구조

```text
센서/기체 ──> FC(상태 추정·안정화·항법·페일세이프) ──> 서보/ESC
                 │
                 │ 시각이 붙은 상태·센서·조종 입력
                 ▼
       별도 추론 MCU 또는 자원 여유가 검증된 FC 태스크
       ├─ 수신·시간 정렬·유효성 검사
       ├─ 학습과 같은 필터·정규화·시간 창 생성
       ├─ TFLM 모델 + 필요한 연산자 + tensor arena
       ├─ 출력 범위·신선도·지속시간 검사
       └─ 로그/경고 ──> 조종자·지상국
                      (후속 단계) 제한된 상위 목표값 ──> FC
```

- **권장 배치:** FC와 별도 MCU를 기체가 지원하는 UART/CAN 링크로 연결한다. 추론 MCU가 중단되어도 FC가 비행을 지속할 수 있어야 한다. ArduPilot과 PX4는 FC와 별도 컴퓨터를 연결하는 구조를 문서화한다. [ArduPilot](https://ardupilot.org/copter/docs/common-companion-computers.html), [PX4](https://docs.px4.io/main/en/companion_computer/)
- **FC 내부 배치:** 대상 보드의 CPU, RAM, 플래시, 스케줄러 여유를 측정한 뒤 선택한다. 추론의 최악 지연이 기존 제어 태스크 마감시간을 침범하면 안 된다.
- **이미 리눅스 컴퓨터가 있다면:** 같은 데이터·검증 절차를 적용하되, MCU용 TFLM이 그 컴퓨터에 적합한 런타임인지 별도로 판단한다.
- **연결 순서:** 처음에는 FC→추론부 데이터와 추론부→로그/경고만 허용한다. 이후 제어 연동 시에도 서보 PWM을 직접 만들지 않고, FC가 검사할 수 있는 상위 목표값만 전달한다. 조종자 전환과 기존 페일세이프의 우선권은 FC에 둔다.

## 3. 핵심 개념과 설계 계약

1. **입력 계약:** 신호 이름, 단위, 좌표계, 주기, 타임스탬프, 결측 처리, 허용 지연을 명시한다. GPS 지상속도와 피토관 대기속도는 구별한다.
2. **전처리 일치:** 학습·평가·펌웨어가 같은 필터, 정규화 계수, 시간 창, 피처 순서를 사용한다. 전처리 버전을 모델과 함께 관리한다.
3. **모델 선택:** 작은 MLP나 1D 시계열 모델부터 시작한다. 변환 후 TFLM이 지원하는 연산자만 쓰는지 확인한다. 대표 데이터로 정수 양자화를 교정하고 변환 전후 출력 차이를 측정한다. [지원 연산자·변환 제약](https://github.com/tensorflow/tensorflow/blob/master/tensorflow/lite/g3doc/microcontrollers/build_convert.md), [대표 데이터](https://ai.google.dev/edge/api/tflite/python/tf/lite/RepresentativeDataset)
4. **메모리와 시간:** 모델의 플래시 공간, `tensor_arena`의 RAM, 입력·통신 버퍼, 스택을 각각 산정한다. 실제 보드에서 arena 사용량, 추론 최악 지연, 전력·온도를 측정한다. [TFLM 메모리 구조](https://github.com/tensorflow/tflite-micro/blob/main/tensorflow/lite/micro/docs/online_memory_allocation_overview.md), [메모리 계측](https://github.com/tensorflow/tflite-micro/blob/main/tensorflow/lite/micro/recording_micro_interpreter.h)
5. **출력 계약:** 점수의 의미, 경고 임계값, 연속 확인 횟수, 유효 시간, 센서 이상 시 무효 처리 규칙을 정의한다. 추론 실패 또는 오래된 입력의 출력은 폐기한다.
6. **변경 추적:** 기체 설정, 센서 보정, FC 펌웨어, 데이터셋, 모델, 전처리, 양자화 파라미터, 추론 펌웨어의 버전을 한 실험 기록에 묶는다.

## 4. 구현 절차와 완료 조건

| 단계 | 작업 | 완료 조건 |
| --- | --- | --- |
| 0. 기체 조사 | FC/펌웨어, MCU, 자원, 센서, 포트, 전원, 로그, 조종권·페일세이프 확인 | 신호·자원·인터페이스 목록과 첫 기능의 성공 기준 작성 |
| 1. 비행 기록 | 정상 운용 범위의 로그 수집. 기체 상태, 조종 입력, 센서 품질, 환경, 타임스탬프 확보 | 각 로그의 기체·날짜·비행 구간·보정 상태 식별 가능 |
| 2. 데이터셋 | 비행 단위로 학습/검증/시험 분리. 중첩 시간 창의 데이터 누출 방지. 드문 사건은 레이블 근거 기록 | 데이터 정의서와 독립 시험 세트 고정 |
| 3. 기준선과 학습 | 간단한 규칙/물리 기반 기준선과 작은 모델 비교 | 기능에 맞는 오탐·미탐·지연 지표가 기준선보다 개선 |
| 4. 변환·교차 검증 | `.tflite` 변환, 대표 데이터 양자화, 지원 연산자 확인, PC와 MCU 출력 비교 | 출력 차이가 허용 범위 안이고 보드의 메모리·시간 예산 충족 |
| 5. 통합·시뮬레이션 | FC 인터페이스와 로그/경고 연결. 누락·지연·고정값·비정상 범위·추론 오류 주입 | 추론 실패가 FC 제어를 방해하지 않고 무효 출력이 전파되지 않음 |
| 6. 지상·비행시험 | 지상에서 전원/재시작/링크 단절 확인. 비행 중 먼저 **그림자 모드**(판단만 기록), 이후 경고 기능 평가 | 새 비행·바람·배터리 조건에서도 사전 정의한 성능·지연·복귀 기준 충족 |
| 7. 제한적 운용 | 필요성이 입증되면 상위 목표값 연동을 별도로 설계·검토 | FC의 범위 제한, 조종자 우선권, 타임아웃, 복귀 동작 반복 검증 |

ArduPilot Plane이라면 [Plane SITL](https://ardupilot.org/dev/docs/plane-sitlmavproxy-tutorial.html)에서 기능과 장애 상황을 먼저 재현할 수 있다. PX4를 쓴다면 [기체별 페일세이프 설정](https://docs.px4.io/main/en/config/safety)을 확인한다. 시뮬레이터 결과는 실기체 시험을 대체하지 않는다.

## 5. 기록과 판정 기준 예시

첫 기능이 비행 상태/이상 징후 모니터링이면 다음을 기록한다.

- 원시 신호: 타임스탬프, 비행 모드, 대기속도(있을 때), GPS 속도, 고도, 자세·각속도, 스로틀·조종면 명령, 전압·전류, 센서 품질 플래그.
- 전처리 산출물: 동기화된 시간 창, 각 신호의 유효성, 정규화된 피처, 모델 입력 배열.
- 결과: 모델 점수, 경고 여부, 추론 시간, 모델/전처리 버전, 오류 및 입력 폐기 사유.
- 평가: 비행시간당 오경보, 확인된 이상 사건의 탐지율과 선행 시간, 조건별 성능, 입력 누락 시 무효 처리율. 정확도 하나만 보고 채택하지 않는다.

임계값, 샘플 주기, 시간 창 길이, 허용 지연, RAM/플래시 한도는 **기체와 첫 기능 확정 후 실측으로 결정**한다. 예를 들어 추론 주기가 100 ms라면 통신·전처리·추론·검사와 여유 시간의 합이 최악 조건에서도 100 ms보다 짧아야 한다. 100 ms는 설계 예시이지 권장 주기가 아니다.

## 6. 기체별 설계를 위해 필요한 정보

1. 기체 형식과 운용 목적, 현재 FC/펌웨어 및 보드 모델.
2. 추론을 올릴 MCU/보드 후보, RAM·플래시·전원·UART/CAN 포트.
3. 보유 센서(특히 대기속도계·전류계)와 비행 로그, 로그 주기.
4. 첫 기능 하나의 입력·출력·오경보 허용치·판단 주기.
5. 수동 조종 복귀 수단, 현재 페일세이프 설정, 시험 가능한 시뮬레이터와 비행 조건.

이 정보로 신호 계약, 데이터셋 스키마, 보드 메모리 예산, 최소 모델, 펌웨어 태스크, 시험 항목을 기체에 맞게 구체화한다.
